# Reckoner v1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Deliver an evidence-backed Reckoner v1 and an honest measured comparison against the frozen v0 baseline through Touchstone.

**Architecture:** Reckoner assembles time-valid Postgres/Neo4j evidence, calls Jev, and uses LangGraph to persist decisions and optional Anthropic notes. One Next.js app supplies review/settings/measurement surfaces. Touchstone receives generic OTLP only and publishes governed DuckDB results.

**Tech Stack:** Python 3.12, uv, FastAPI, Postgres 17/pgvector, Neo4j/GDS, LangGraph, Jev, Anthropic via LiteLLM, DeepEval, Ragas, existing OTel/ClickHouse/dbt/MetricFlow/Dagster, Next.js/TypeScript, Compose and kind.

**Spec:** [004-reckoner-v1.md](../../spec/004-reckoner-v1.md), approved 2026-09-30. Foundation and Phase 2 contracts remain applicable.

**Status:** Approved by the owner on 2026-09-30, including the three linked stage plans, with subagent-driven execution. Paid-run protocols require their own concrete approval.

## Global Constraints

- Preserve simulated-data labels, the 1,000-case 2019 cohort (100 fraud / 900 legitimate), original baseline artifacts, and two-tenant assignment. USD/UTC remain experimental assumptions.
- `tenant_id` belongs on every persisted application/event row and graph node, including v1 checkpoints, review records, and configurations. Operational joins include it. Platform ingestion is OTLP only.
- Historical evidence must precede query time strictly. Historical simulated resolution is transaction time plus seven days, also strictly before query time. No current/future oracle labels in runtime inputs.
- Binary Jev Choice, initial `jev-1.13.0`; initial note/judge model `anthropic/claude-haiku-4-5-20251001`. No floating aliases, substitute scorer, new embedding provider, or live Snowflake work.
- Defaults: review cost `4.00`, margin `.30`, low floor `.005`, low ceiling `.05`, high `.90`, amount-aware true. Flat low is `.05`; equal boundaries escalate.
- Risk indicators cite evidence and their deterministic method; they are not model attribution. Pgvector uses structured feature similarity.
- Note gates: schema validity 100%, note-only verdict agreement at least 90%, mean faithfulness at least .90, all expected cases accounted for. Missing/error/zero-population results never become passes.
- Preserve the Anthropic ledger: 1,040 settled calls, USD .493151. Jev credits are owner-reported USD 10, not verified billing. Explicit bounded paid-run approval is separate from plan approval.
- 8 GB RAM / 4 GB swap; Compose and kind separately. Preserve all measured volumes, backups, source files, worktrees, and prior images. No global Docker cleanup.
- Start implementation in `feat/phase-3-reckoner-v1`, worktree `.worktrees/phase-3-reckoner-v1`, based on the approved documentation commit descending from `de706d6`. Verify the base before creating it; do not reset an existing branch.
- Configure the feature branch's upstream to its own remote branch only when publishing. Never track `origin/main` as the feature branch upstream. The owner handles push/merge.
- Each numbered task: fresh implementer, RED → GREEN, self-review, independent review, focused commit. Dependent tasks are sequential. Reviewers do not edit code; a fix returns to its implementer.
- Only documentation is changed while preparing this plan. Read-only inventory results below are feasibility evidence, not a frozen dataset bundle or a measured provider run.

## Review Focus

1. A provider responds before the worker crashes: restart must use persisted response/accounting rather than issue a duplicate paid call (A4, B6).
2. Historical rows tie at the cutoff, resolve at exactly seven days, or appear in a later GDS projection: earlier queries must exclude them (A2–A3).
3. Two reviewers/settings editors race or retry after a lost response: one immutable action/version wins; stale writes are visible conflicts (B8–B9).
4. Model settings change after a run starts, or notes settle after decisions: the run retains its configuration and final cost stays incomplete until billing is known (B6, B8, C10).
5. Tenant/run/case IDs contain separators or markup, and evidence bodies contain hostile instructions: IDs remain opaque data, and neither oracle/secret data nor unsafe markup reaches the UI/provider (A1, A4, B7–B9).

## Shared interface conventions

New operational records use strict schemas and Python `dict` documents, with
`Decimal` only inside calculations and decimal strings at JSON boundaries. Task 1
defines their fields in schemas. Do not invent a generic repository framework.
All references use `(tenant_id, run_id, task_id)` or `(tenant_id, case_id)` explicitly.
Canonical identities use the existing `reckoner.contracts.content_id` helper.

Use new focused modules under `reckoner/v1/` for the workload, keeping the existing
baseline modules stable. Only pure cost-evaluation functions may be reused across
v0/v1. The existing large `storage/postgres.py` is not expanded into a second
workflow implementation. New v1 persistence lives under `reckoner/v1/storage/`.

Operational API uses `/v1/cases`, `/v1/case`, `/v1/reviews`, `/v1/configurations`,
`/v1/configurations/activate`, and `/v1/configurations/preview`, with tenant/run/case
identifiers in validated query parameters or JSON bodies. This avoids treating an
opaque slash-containing identifier as a path hierarchy. Existing v0 routes remain.

CLI additions are under `reckoner v1`: `prepare`, `import`, `score`, `calibrate`,
`run`, `evaluate`, `review-simulated`, `export`, `benchmark`, `protocol`, `verify`.
Each task defines its own argument contract below. Preparation and reports are
atomic publications to a new output directory; never overwrite a frozen artifact.

## Paid execution gates

Task 13 creates reviewable protocol files after exact manifests and token bounds
exist. Proposed order: 20-case Jev pilot; 2,000 development scores; 2,000 validation
scores; 200-case paired graph comparison; 20-case note/judge pilot; final 1,000-case
comparison and all resulting note evaluations. Counts refer to unique cases, not
retry attempts. Reuse identical persisted inputs/responses where the protocol says
so, but label reused costs and latencies; never report replay latency as live latency.

Calibration uses the relational/vector evidence arm. Its fitted map cannot simply
be transferred to a GDS-augmented scorer. If the paired experiment favors a changed
input definition, that definition needs its own approved full development and
validation scoring/calibration pass before the final run. If unchanged, use the
existing qualification. This is a dependency gate, not automatic extra spending.

Full-cohort note count is unknown until routing. The final-run proposal must bound
up to 1,000 escalations, or stage scoring first and then present the exact resulting
note case IDs and cost bound. An exhausted budget leaves notes/evals incomplete;
do not assume only 2–5% of transactions will escalate.
